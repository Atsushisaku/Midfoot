# デッドリフト動作エラー提示アプリ 要件定義（v0.2）

作成: 2026-08-03 / 状態: **方針決定済み。§9 に残る論点あり**

Midfoot デッドリフト版（`/deadlift.html`）の次段階。骨格から最適フォームを出すところまでは
できたので、次は**インストラクターがクライアントのエラーを指摘・明示しやすくする**道具を作る。

## 0. 決定事項（2026-08-03）

| 論点 | 決定 |
|---|---|
| 体幹の分節 | **しない**。L5/S1 を体幹上の点としてだけ定義し、腰のモーメントアームを出す。「背中が丸い」は対象外 |
| 時間軸 | **持つ**。動作全体を扱い、バー高と腰高の進み方を分離する |
| 配置 | **3 本目の独立ページ**（インストラクター向け。一般公開ページとは UI 密度も利用者も違う） |
| 第1弾のエラー | ① バーが身体から遠い ② ぶっこ抜き（ヒップシュート） ③ 腰が高すぎる／低すぎる |

ロックアウトの反り返り／ソフトロックは実装が軽い（`TORSO_TOP_DEG` を振るだけ）ので、
第1弾が動いたら**おまけとして追加**する候補に置いておく。

### 0.1 追加決定（2026-08-03、プロトタイプ評価後）

| 論点 | 決定 |
|---|---|
| 操作方式 | **カタログのみ**。逸脱パラメータのスライダーは UI から撤去する（§5.1） |
| カタログの項目 | **3 つ**：ぶっこ抜き／上体の立てすぎ／バーが遠い |
| 程度 | **軽度・中等度・重度の 3 段** |
| 主指標 | **脚の伸展の使用率**（§11.1）。梃子より先に、これを大きく出す |

## 1. 目的と利用シーン

- **利用者**: インストラクター（クライアントに説明する側）
- **場面**: 指導中またはフィードバック時に、画面を見せながら「いまこうなっている／本来はこう」を示す
- **中心の体験**: **最適フォームとエラーフォームを並べて比較**し、
  「動作のどこで」「幾何・力学的に何が起きていて」「だから何が悪いのか」を示す

### 1.1 このアプリが引き継ぐべき主張

Midfoot の主張は「**最適フォームは体格の関数である**」。
したがってエラーも**絶対的な基準ではなく、その人の最適フォームからの逸脱**として定義する。

これは飾りではなく設計を縛る。「けつが下がりすぎ（上体を立てすぎ）」は
**体格によっては最適**になりうる（大腿が短く体幹が長い人の最適は上体が立つ）。
絶対角度で「背角 60° 未満はエラー」とやると、既存アプリの主張と矛盾する。

→ **エラー量は「その体格の最適値からの差分」で持ち、表示も差分で出す。**

## 2. エラーの棚卸し

◎＝現行モデルでそのまま／○＝拘束を外せば可能／△＝モデル拡張が必要／✕＝2D 剛体では不可。
**★＝第1弾で実装**。

### A. セットアップ（静止姿勢）

| # | エラー | 表現 | 備考 |
|---|---|---|---|
| A1 ★ | バーが足から遠い（前すぎ） | ○ | `bar.x ≡ midX` の拘束を外す |
| A2 ★ | 腰が高すぎる（スティフレッグ気味） | ◎ | `hipHeight` を基準より上へ |
| A3 ★ | 腰が低すぎる（上体を立てすぎ・スクワット的） | ◎ | `hipHeight` を基準より下へ |
| A4 | 背中が丸い（脊柱の屈曲） | △ | **対象外**（体幹は 1 剛体のまま） |
| A5 | 肩がバーより前／後ろすぎ | ○ | 現行は出力。入力にする必要あり |
| A6 | かかと荷重／つま先荷重 | ◎ | `comPos` |
| A7 | スタンスが広すぎ／狭すぎ | ◎ | `stanceDeg` |
| A8 | 膝が前に出すぎてバーに当たる | ○ | Rev.6 のクリアランス・キャップで構造的に排除済み。見せるならキャップ解除が要る |
| A9 | 顎が上がる／目線 | ✕ | 頭部が装飾で関節を持たない |

### B. バー軌道

| # | エラー | 表現 | 備考 |
|---|---|---|---|
| B1 ★ | バーが体から離れていく（前へ流れる） | ○ | A1 に時間軸を付けたもの |
| B2 | バーが膝で引っかかる／迂回する | ○ | キャップ解除が要る |
| B3 | バーが足側へ戻る | ○ | 同上 |
| B4 | 軌道が蛇行する（無駄な移動距離） | ○ | B1〜B3 の合成 |

### C. 順序・タイミング

| # | エラー | 表現 | 備考 |
|---|---|---|---|
| C1 ★ | ぶっこ抜き／ヒップシュート（ファーストプルのキャンセル） | ○ | §3.3 の `hipLead` で表現 |
| C2 | 腰が落ちてから引く（ダブルモーション） | ○ | `hipLead < 0`。C1 と同一パラメータの逆側 |
| C3 | 膝が先にロックしてスティフレッグで引く | ○ | `hipLead` の極端値 |
| C4 | ロックアウトの反り返り（過伸展） | ○ | `TORSO_TOP_DEG` を振る。第1弾の次 |
| C5 | ロックアウトしきらない（ソフトロック） | ○ | 同上 |

### D. 幾何モデルの外（対象外）

腹圧・呼吸（D1）、グリップ・手幅（D2、矢状面 2D のため）、左右差（D3、左右対称の見なし）、
ラットの緩み（D4）。

## 3. モデル設計

### 3.1 ソルバを 2 本立てにする

現行 `solveDlPose` は「拘束を満たす姿勢を解く」**逆問題**。その拘束は
`bar.x ≡ midX` / 身体重心 = 目標 / 膝は `(hipHeight, t)` の固定スケジュール、などで、
**エラーとはまさにこれらの拘束が破れた状態**。だから現行ソルバの延長では出せない。

| | 最適フォーム（既存） | エラーフォーム（新規） |
|---|---|---|
| 問題の向き | **逆問題**：拘束を満たす姿勢を解く | **順問題**：逸脱を与えて姿勢と帰結を計算する |
| 入力 | 体格・スタンス・進行度 | 体格・スタンス・進行度 ＋ **逸脱パラメータ** |
| 出力 | 姿勢 | 姿勢 ＋ **力学的な帰結** |
| 実装 | `solveDlPose` を**無改造で残す** | 新規モジュール。体節長の正規化だけ共有 |

既存ソルバを壊さないことは実務上も重要で、テストが**両種目共通のデプロイゲート**になっている
（デッドリフト側を壊すとスクワット版の公開も止まる）。

### 3.2 逸脱パラメータ（第1弾）— **内部表現。UI には出さない**

いずれも **0 が最適フォーム**。カタログの各項目がこれらの束（症候群）として定義される。

| パラメータ | 範囲 | 意味 |
|---|---|---|
| `barOffset` | −2〜+10 cm | バー x を中足部から前方へずらす量。正＝前 |
| `hipLead` | −1〜+1 | 腰の先行度。正＝ヒップシュート、負＝腰が落ちる |
| `hipDelta` | −0.5〜+0.5 | `hipHeight` の基準（0.5）からの差分。**構えにしか効かない** |
| `ignoreBarClearance` | bool | クリアランス・キャップを外す（§10-D） |

`hipDelta` は構えだけ、`hipLead` は動作中だけに効く（前者はキャップに吸収され、
後者は t でランプする）。**この 2 つは対になっていて、両方入れて初めて
「構えから崩れていて、動作中も崩れ続ける」が描ける**。カタログの束ね方はこれに従う。

### 3.3 腰の先行（`hipLead`）の実装 — **プロトタイプで方針変更**

当初は「バー高は `t` で進め、脚の伸展スケジュールだけ `t' = warp(t, hipLead)` で早送りする」
という時間ワープで書いた。**実測したところ何も変わらなかった**（§10-A）。

確定した実装は 2 段:

1. **膝**: キャップ後の最適値を、脚の伸展の終端（正）／始端（負）へ内分する
2. **股関節**: 到達可能な φ の範囲を走査し、`hipLead = ±1` をその端に対応させる

さらに `hipLead` は `t` でランプさせる（`smoothstep(0, 0.2, t)`）。ぶっこ抜きは
「セットアップは悪くないのにファーストプルが飛ぶ」動作なので、**t=0 は最適と一致**させ、
バーが床を離れた直後から崩れ始めるのが実像に合う（セットアップ自体が腰高いのは
`hipHeight` 側の別エラー）。

### 3.4 L5/S1 の定義

体幹は分節しないが、腰の負荷を語るための点として置く。

- 体幹（股関節→肩）の直線上、**股関節から体幹長の 10〜15%** の位置に置く
- **正確な比率は出典を当ててから決める**（§9）。暫定 0.12
- 実際の L5/S1 は股関節中心よりやや後方にあるが、矢状面 2D では体幹の線上に載せる近似とする。
  この近似はモデルの但し書きに明記する

## 4. 出力：「何が悪いか」をどう示すか

文章で「腰に悪い」と書くのでは既存の解説記事と変わらない。**数値で出せることが差別化**になる。

### 4.1 第1弾の指標（質量の仮定を一切置かない）

| 指標 | 意味 |
|---|---|
| バー → L5/S1 の水平距離 | **バーの重量**が腰にかける梃子 |
| 上体重心 → L5/S1 の水平距離 | **上体自身の重さ**が腰にかける梃子（§10-C で追加） |
| バー → 股関節 の水平距離 | 股関節伸展のモーメントアーム（ハム・臀筋） |
| バー → 膝 の水平距離 | 膝伸展のモーメントアーム（大腿四頭筋） |
| 背角（水平から） | 上体の寝かし具合。姿勢系エラーの主な指紋（§10-C / E） |
| バー → 脛 の水平距離 | クリアランス。負ならバーが脛に食い込んでいる |
| バーの総移動距離 | 軌道の無駄 |

表示は **cm と「最適比 +N%」の併記**。例:
「バーが 5cm 前 → 腰の梃子（バーの重量）34.6cm（最適比 **+17%**）」

**腰の梃子を 1 本にまとめてはいけない**（§10-C）。バーの梃子と上体自重の梃子は
エラーによって逆向きに動く。合算するにはバー重量と体重の比を仮定する必要があり、
第1弾では仮定を持ち込まないので**分けたまま出す**。この但し書きは UI にも出している。

### 4.2 第2弾の候補（バー重量／体重比のスライダーを足す場合）

- 合成重心（身体＋バー）の x が支持基底のどこに落ちるか。前に出るほど「つま先に乗る／
  かかとが浮く」。**「重いほど崩れる」が見えるのは指導上おもしろい**
- L5/S1 まわりの総モーメント（バー＋上体質量）

### 4.3 「動作のどこで」を示す

要望「デッドリフト動作の**ここで**エラーとなる」への対応。

- 各指標を `t` に対して計算し、**最適との差が最大になる点を自動でマーク**する
- 「ここが一番まずい」ボタンでスライダーをその点へ飛ばす
- 時系列は最低でも「最適 vs エラー」の 2 本の折れ線で出す

## 5. UI 構成

既存の 2 体比較の枠を流用する。

### 5.1 スライダーは出さない（2026-08-03 決定）

逸脱パラメータのスライダーを UI に出すと、インストラクターは
「バー前方 3.0cm ／ 腰の先行 0.60」という**内部表現**を操作することになる。
これは §7.3 で「混ぜるな」と書いた原因と現象の混同そのもので、指導の道具として使えない。

**UI に出るのは「現象の名前」と「その程度」だけ**にする。

| UI に出す | UI に出さない |
|---|---|
| エラー名（ぶっこ抜き／上体の立てすぎ／バーが遠い） | `barOffset` / `hipLead` / `hipDelta` |
| 程度（軽度／中等度／重度） | キャップの有無 |
| 帰結（脚の伸展の使用率・梃子・背角…） | |

カタログの 1 項目は**複数パラメータの束**になる（`src/error/catalog.ts`）:

| 項目 | 束ねている逸脱 | 根拠 |
|---|---|---|
| ぶっこ抜き | 腰高セッティング ＋ 腰の先行 ＋ バーの前流れ | §11.1。3 つは併発ではなく幾何的に連動している |
| 上体の立てすぎ | 腰低セッティング ＋ 腰の落ち ＋ バーが手前 | §11.2 |
| バーが遠い | バーの前方オフセットのみ | セットアップ単独で起きるので独立させる |

```
┌────────────────────────────────────────────────┐
│   [最適フォーム]              [エラーフォーム]         │
│    （青）                      （コーラル）            │
├────────────────────────────────────────────────┤
│  ▶再生   時間 ──────●───────  25%              │
│                                                │
│  体格（両者共通） [標準][大腿が長い][体幹が長い] 腕 …    │
│                                                │
│  エラー [なし][ぶっこ抜き][上体の立てすぎ][バーが遠い]   │
│         程度 [軽度][中等度][重度]  [ここが最大乖離]     │
│                                                │
│  腰が先に上がって上体が寝る。脚の伸展を序盤で使い切る…    │
│                                                │
│  バーの進み 25% の時点で、脚の伸展を 30% ／ 46% 使用   │
│                                （脚を先食いしている）  │
│                                                │
│  指標              最適    エラー    差             │
│  腰の梃子｜バーの重量 27.6cm  25.7cm   −7%          │
│  腰の梃子｜上体の自重 21.5cm  23.2cm   +8%          │
│  …                                             │
└────────────────────────────────────────────────┘
```

- **「エラーなし」のときは帰結まわりを丸ごと畳む**（2 体が同一なので見せる意味がない）
- 複数エラーの重畳は**第1弾では持たない**。カタログ 1 択にして操作を単純に保つ

## 6. スコープ外（明示）

- 動画・写真からの姿勢推定（入力は手動）
- 左右差、グリップ、呼吸・腹圧
- 絶対的な負荷（Nm・kg）の算出（§4.1 の理由）
- 「背中が丸い」（§0 の決定）
- **医学的な傷害リスクの断定**。言えるのは「腰のモーメントアームが N% 増える」までで、
  「腰を痛める」は言えない。**文言をここで止める規律を要件に含める**

## 7. リスク・懸念

### 7.1 `hipHeight = 0.5` は「最適」ではなく「規約」（要注意）

現行アプリは `hipHeight: 0.5` をハードコードしていて、その根拠は Rev.4 の
**「シャフトが脛に触れる位置」という規約**であって、何かを最小化した結果ではない。

「腰が高すぎる／低すぎる」を**エラーとして N% の悪化つきで断定する**なら、基準側にも
根拠が要る。このアプリでモーメントアームを計算できるようになるので、
**`hipHeight` を「モーメントアームの合計（またはピーク）を最小にする値」として導出できる**
可能性がある。そうなれば 0.5 は規約から**計算結果**に格上げでき、親アプリの主張も強くなる。

→ 第1弾では 0.5 を基準として使い、**この導出は別途検討**とする（§9）。

### 7.2 「エラー」と断定することの重さ

親アプリは「最適は体格で変わる」と言っている。そこへ「これはエラー」を重ねると、
モデルの精度以上の断定に見えるおそれがある。2D・筋なし・脊柱なしという前提を
注記で常時見せる（既存の「注記」ボタンの枠が使える）。

### 7.3 エラーの「原因」と「現象」を混ぜない

要望に「エラーが出る要因をパラメータに」とあったが、**原因**（股関節の可動域不足、
ラットが弱い、キューの誤解）と**現象**（腰が先に上がる）は別物。
パラメータは**観察できる現象**（＝動画で見える逸脱）で持ち、原因と修正キューは
テキストの層として別に持つ。混ぜるとモデルが破綻する。

## 9. 残る論点

1. **L5/S1 の位置比率**の出典（暫定 0.12）

## 10. プロトタイプで分かったこと（2026-08-03）

P1〜P3 を一気に作って実測した。**要件の想定が 4 つ覆った**ので記録する。
実装は `src/error/{app,metrics,catalog}.ts` ＋ `deadlift-errors.html`。

### A. 時間ワープでは「ぶっこ抜き」は表現できなかった

挙上の中盤（t≈0.3〜0.6）は **Rev.6 のクリアランス・キャップが膝位置を完全に支配**していて、
脚の伸展スケジュールを早送りしても `min()` がキャップを拾うので姿勢が 1mm も動かなかった。
キャップは「バーが脛に当たらない」という物理なので外せない。→ §3.3 の 2 段構えに変更。

### B. 膝を動かすだけでは足りず、股関節を規定する必要があった

膝だけ内分しても背角は 3.7° しか動かない。腰の高さと背角を決めているのは膝ではなく
**大腿角 φ** で、そこは重心拘束が握っているため。φ を規定して**重心のほうを出力に落とす**
ことで、はじめて要件 §3.1 の「順問題」になった。

φ の与え方も 2 回失敗している。(1) ロックアウト値へ内分 → 肩がバーの 40cm 前へ飛び出し、
しかも hipLead に対して非単調。(2) 「腰を N cm 上げる」と決め打ち → 上げる余地がない t で
破綻枝を拾って逆戻り。**到達可能な φ の範囲を実際に走査して端を求める**形にして解決した。
限界の判定は腕の前傾 20° で置いている（肩の絶対位置より物理的な根拠がある）。

### C. モーメントアームは 1 本では足りない。「バーの梃子」と「上体自重の梃子」に分ける

ぶっこ抜きを実測すると、腰が上がって L5/S1 がバーに近づくので
**バーの梃子はむしろ 24% 縮む**。それでもぶっこ抜きが腰にこたえるのは、
上体が寝たぶん**上体自身の重さの梃子が伸びる**から（+11%）。
両方とも質量比の仮定なしに幾何だけで出せるので、分けて表示することにした。

これに伴い「動作のどこで」の判定（要件 §4.3）も、バーの梃子だけで測ると
最大乖離点が外れる。**2 本の梃子の差の絶対値の合計**で測る。

### D. 「けつが下がりすぎ」はキャップを外さないと表現できない

`hipHeight` を下げると膝が前に出るが、キャップが全部吸収して姿勢が変わらなかった
（0.5→0 で背角 +1°、腰高 変化なし）。キャップは**上手い人がやっていることを
モデルに埋め込んだ制約**なので、エラー側では外す（`ignoreBarClearance`）。
外した結果バーが脛に近づくことは指標（`barToShinCm`）に出す。

### E. 「バーが遠い」の指紋は背角ではなく梃子だった

当初は「肩が前へ届くぶん股関節が後ろへ逃げて背中が寝る」と書いたが、**背角はほとんど動かない**
（+8cm で 1° 未満）。しかも重心拘束をそのまま使うと、腕の重心が前へ出たぶんを打ち消すように
体幹が後ろへ回り、**バーを前に置くほど上体が立つ**という逆の絵が出た。

実際の人は「バーが遠いぶん自分の釣り合いを取り直す」のではなく
**いつもどおり構えて遠いバーへ手を伸ばす**ので、釣り合い（φ の決定）は
意図した位置＝中足部で解き、肩だけを実際のバーから取り直す形にした。

### 実測したエラーの指紋（標準体格・ミドルスタンス）

| 指標 | バーが遠い(5cm, t=0) | ぶっこ抜き(0.8, t=0.35) | 腰が低い(−0.35, t=0) |
|---|---|---|---|
| 腰の梃子｜バーの重量 | **+17%** | −24% | −2% |
| 腰の梃子｜上体の自重 | +1% | **+11%** | −6% |
| 股関節の梃子 | **+14%** | −18% | −3% |
| 膝の梃子 | −52% | **+129%** | **+54%** |
| 背角 | +1% | **−35%** | **+14%** |
| バー → 脛 | **+158%** | +72% | **−27%** |

**3 つのエラーがそれぞれ違う指紋を持つ**ことは確認できた。ここが P1 の合否だったので、
アプリとしては成立している。

### 残る限界

- `hipHeight`（腰の高さ）は**セットアップにしか効かない**。t≥0.2 ではキャップが支配して
  最適と一致してしまう。実際には腰高いセットアップはプル全体に尾を引くので、ここは未表現
- 腰を上げると肩は前へ滑るが、**本当はその時点でバーが体から離れ始める**（バーは手に
  ぶら下がっているため）。エラーが別のエラーを誘発する連鎖はモデル化していない
- L5/S1 は体幹長 12% の暫定値のまま

## 11. エラー解釈の検証（2026-08-03）

atsushi さんの「主なエラーは 2 つ」という整理をモデルで検証した。**測れたもの／測れなかったもの**を分ける。

### 11.1 ぶっこ抜き

| 主張 | 判定 | 根拠（標準体格・ミドル） |
|---|---|---|
| 腰が先に上がる | **○** | t=0.2 で腰高 70→80cm、背角 33→16° |
| ファーストプルは軽くなる | **○** | t=0.2 でバーの腰への梃子 28.1→19.9cm（−29%） |
| セカンドで詰まる | **○（ただし梃子では説明できない）** | 下記 |
| セッティングの腰高とほぼ同じ | **△（半分）** | 下記 |
| バーが遠くなりがち | **◎（機構まで出る）** | 肩がバーの前へ 8.2→19.5cm、腕の傾き 7.3°→17.5° |

**「セカンドで詰まる」の正体は梃子ではなく脚の使い切り。** 梃子はむしろ全域で縮むので、
梃子で説明しようとすると「楽になる」という逆の結論になる。実際に出るのは膝関節角:

| バーの進み | 最適 | ぶっこ抜き | 立てすぎ |
|---|---|---|---|
| t=0.2 の時点で使った脚の伸展 | 25% | **55%** | **11%** |
| t=0.5 | 48% | 66% | 43% |

**バーがまだ 20% しか上がっていないのに脚の伸展を 55% 使い切っている**。残りは背中で引くしかない
＝これが「セカンドで詰まる」の幾何的な正体。この 1 本の指標で 2 つのエラーが逆向きに出る
（立てすぎは 11% ＝ 脚が遅れる）ので、**アプリの主指標はこれにする**。

**「腰高セッティングと同じ」は半分。** 中盤の姿勢は確かに収束するが、**時間の出方が逆**:

| t | 最適 | ぶっこ抜き | 腰高セッティング |
|---|---|---|---|
| 0 | 背34° 腰59 | 背34° 腰59（**同一**） | 背28° 腰64（**ここが違う**） |
| 0.2 | 背33° 腰70 | 背16° 腰80（**ここが違う**） | 背33° 腰70（同一） |

インストラクターが 2 つを見分ける手がかりはまさにここ（セットアップを見るか、床を離れた瞬間を見るか）。
ただし**「腰高セッティングが t≥0.2 で最適に戻る」のはモデルの欠陥**（§10-A のキャップ）で、
実際には尾を引く。**2 つを 1 つのカタログ項目に統合すればこの欠陥を回避できる**ので、
統合という判断はモデル的にも都合がよい。

### 11.2 上体の立てすぎ

| 主張 | 判定 | 根拠 |
|---|---|---|
| 腰が低いセッティングと同じ | **○** | 幾何的に同一。t=0 で背角 34→41°、膝角 94→85° |
| バーも近くなりがち | **○（「脛とバーがぶつかる」と同じこと）** | バー→脛 3.2→2.0cm（t=0）、**t=0.2 で −1.5cm ＝ バーが脛の内側**。バーは膝を迂回するしかない |
| ファーストプルで力が入れにくい | **△（モデルは姿勢しか示せない）** | 梃子は −2〜−3% でほぼ動かない。膝角 85°（深屈曲）と脚の伸展の遅れ（11%）は出せるが、**「力が出ない」理由（筋長・筋の作用効率）は 2D 骨格モデルの外** |

### 11.3 その他のよくあるエラー（調査）

| エラー | 頻度 | モデルで出せるか |
|---|---|---|
| **背中が丸い**（胸椎・腰椎） | 最多クラス | **✕**（体幹 1 剛体。§0 で対象外と決定済み） |
| ぶっこ抜き（英: stripper hips） | 最多クラス | ○ 実装済み |
| バーが体から離れる | 高 | ○ 実装済み |
| 上体の立てすぎ／腰が低い | 高 | ○ 実装済み |
| **スラックを抜かずに引く**（バーが鳴る） | 高 | **✕**（張力の話で幾何ではない） |
| バーが膝に引っかかる／迂回する | 中 | ○（上の 2 つの帰結として自動的に出る） |
| ロックアウトで反り返る | 中 | ○ 軽い（`TORSO_TOP_DEG`） |
| かかとが浮く／つま先荷重 | 中 | ○（`comPos`） |
| **スタンスが広すぎ → 膝の内側入り・足部の回内** | 中 | **✕**（前額面。矢状面 2D の外） |
| 顎が上がる／過度に上を見る | 中 | ✕（頭部に関節なし） |
| グリップが先に負ける | 中 | ✕ |
| 左右差（バーが傾く） | 中 | ✕（左右対称の見なし） |
| **下ろしが雑**（エキセントリック） | 中 | ✕（現行は挙上のみ。スコープ要検討） |

出せないものが多いが、**出せる 4 つ（ぶっこ抜き・立てすぎ・バーが遠い・反り返り）で
矢状面のよくあるエラーはほぼ覆えている**。覆えていない中で頻度が高いのは
「背中が丸い」と「スラック」の 2 つ。

### 11.4 下背部の丸まりは独立したエラーか（2026-08-03 の検討）

「丸まりはぶっこ抜きの結果では」という問いをモデルで当たった。
ハム長の粗い代理量として **股関節屈曲量 ＋ 膝伸展量** を取る
（ハムは股関節と膝をまたぐので、股が屈曲するほど・膝が伸びるほど引き伸ばされる）。

**エラー別（標準体格・中等度）**

| t | 最適 | ぶっこ抜き | 上体の立てすぎ | バーが遠い |
|---|---|---|---|---|
| 0（構え） | 220 | 226 | 213 | 220 |
| 0.15 | 227 | **240** | 202 | 216 |
| 0.3 | 227 | **236** | 196 | 211 |

ぶっこ抜きだけがハムの張りを上げる（t=0.15 で最大）。**上体の立てすぎはむしろ下げる**ので、
丸まりの機序としては別物（こちらが丸まるとすれば理由は骨盤の後傾ではない）。

**体格別（構え t=0）**

| | 腕 短 | 腕 標準 | 腕 長 |
|---|---|---|---|
| 大腿が長い | **240** | 233 | 226 |
| 標準 | 225 | 220 | 216 |
| 体幹が長い | 207 | 207 | 205 |

**大腿が長い × 腕が短い**が最も高く、体幹が長い体格の 1.16 倍。
「丸まりやすさは体格の関数」という Midfoot の主張どおりの並びになる。

**結論**: 丸まりは(a)ぶっこ抜きの帰結としても、(b)可動域・体格由来の構えの問題としても起きる。
前者は従属だが**後者は独立**（他が完璧でも構えの時点で丸まる）。
したがって独立したカタログ項目にはせず、**既存項目に付く「丸まりやすさ」の指標**として扱うのが妥当。
体幹を分節しなくても（＝丸まりを描かなくても）この指標は幾何だけで出せる。

**この代理量の限界**: 股関節屈曲と膝伸展を等重みで足しているだけで、実際のモーメントアーム比は
反映していない。可動域の個人差も大きく、**荷重（実際に背中が負けるかどうか）は入っていない**。
姿勢の順位づけには使えるが、個人の予測には使えない。

## 12. フィニッシュの統一と、描写の割り切り（2026-08-03）

### 12.1 エラー 3 項目とも、フィニッシュは模範と一致させる

**エラーのあるフォームは「立ち切った形が違う」のではなく「そこへ至る道のりに無駄が多い」。**
バーは腿に当たるので前には残れないし、膝も股関節も伸び切るしかないので、
ロックアウトはほぼ同じ形になる、という観察にモデルを合わせた。

`ERROR_FADE_START = 0.6` から t=1 にかけて逸脱を 0 へ戻す。対象は
`barOffset` / `kneeAheadExtra` / `hipLead`。角度は Rev.10 の寄せが t=1 で上書きするが、
`hipLead` は膝の前方量にも効いていてそちらは寄せの対象外なので、明示的に掛ける必要があった
（掛けないとフィニッシュの膝が 0.7cm 前に残り、股関節が 1cm ずれた）。

**回帰テスト**: `src/error/catalog.test.ts`。3 項目 × 3 段 × 体格 3 種のすべてで、
t=1 の足首・膝・股・肩・バーが模範と 0.05cm 以内で一致すること。

### 12.2 「上体の立てすぎ」は導出をやめて描き値を置いた

順序は **上体を立てようとする → 尻が落ちる**。脛は**前傾が強くなる**（atsushi さん）。
一度「脛が垂直寄りになる」で作ったが、そちらは一般的ではないとの判断で差し戻した。

`hipHeight` 経由では膝が 1.9cm しか動かず、この見た目に届かなかった（§10-D）。
`kneeAheadExtra`（膝を前後へずらす量、cm）を足し、**正の値**で膝を前へ出して脛を倒す。
**これは力学から導出した量ではなく、そう見えるように置いた値**。
エラーの描写なのでそれでよい、という判断（atsushi さん）。

膝を前へ出すと背中も起きるので、腰の落ち（`hipLead` 負）と**同じ向き**に効く。
上体の立てすぎは**構えの時点ですでに腰が落ちている**ので、`hipLeadRamp: 0` を渡して
構えから効かせる（ぶっこ抜きは逆に、構えは正常なのでランプが要る）。

**3 段の刻み方**（2026-08-04 に調整）:

- **軽度は「構えで腕が床と垂直になる」ところ**に合わせた（実測 腕 0.2°）。
  最適では腕は 5.4° 前傾していて、上体が立つほど肩がバーへ寄って垂直に近づく。
  「腕が垂直」は指導中に目視で判定しやすいので、軽度の基準として使える
- 中等度はそのまま
- 重度は元がきつすぎたので中等度側へ寄せた（構えの背角 65°→60°）

| | 最適 | 軽度 | 中等度 | 重度 |
|---|---|---|---|---|
| 腕の傾き（t=0） | 5.4° | **0.2°** | −3.7° | −7.8° |
| 背角（t=0） | 34° | 45° | 53° | 60° |
| 背角（t=0.15） | 32° | 42° | 51° | 59° |
| 腰高（t=0.15） | 68cm | 61 | 56 | 52 |

**前傾を入れすぎるとバーが上がらないだけ**（脛がバーの通り道を塞ぐ）なので、
中等度でバーが脛に触れる程度、重度で明確に食い込む程度に収めてある。

### 12.4 最適とエラーの数値表は撤去

「特に何の分析にもならない」（atsushi さん）。梃子を 4 本並べても、
インストラクターが指導で使う情報にはならなかった。

残すのは**主指標 1 本**だけ ——「バーの進み N% の時点で、脚の伸展を X% ／ Y% 使用」。
`src/error/metrics.ts` の梃子まわりはモデル層として残してあるが、画面からは呼んでいない。

### 12.3 「ここが最大乖離」ボタンは撤去

**エラーは床を離れた直後にはもう出ている。** 乖離が最大になる時点を探すより前に問題は
見えているので、そこへ飛ぶ操作に意味がない（atsushi さん）。§4.3 の「動作のどこで」は、
時間スライダーを動かせば自然に見えるので、ボタンとしては持たない。

## 13. UI/UX の整理（2026-08-04）

### 13.1 エラーを選んでも図が動かないようにする

エラー未選択のとき説明文と主指標を `hidden` で畳んでいた。すると操作パネルが縮み、
`.stage` が伸びて **図そのものの大きさと位置が変わっていた**（1400×780 で 23px、
狭い画面ではもっと動く）。比較して見るための道具で図が動くのは致命的。

**要素は消さない。中身だけ差し替える。**

| 状態 | 説明文 | 主指標 | 程度 |
|---|---|---|---|
| エラーなし | 「左右とも模範フォーム。…」（灰） | 模範の値だけを 1 つ表示 | 場所は残して淡色・操作不可 |
| エラーあり | そのエラーの説明 | 模範／エラーの 2 つを表示 | 通常 |

説明は **「詳細」という行見出しつきの箇条書き**にした（§13.3）。
高さも **3 行ぶんを先に確保**する（`min-height: calc(1.7em * 3)`、860px 以下では 5 行）。
点数が揃っていないと同じ問題が再発するので、**箇条書きは必ず 3 点・1 点は 1 行**を
`catalog.ts` の型（`readonly [string, string, string]`）とコメントで規約にした。

実測: 1400/1280/1920/1100/900/880/760/600 px のいずれでも、
4 項目を切り替えて図の位置・高さが 1px も動かない。
430px（スマホ）だけ主指標が 2 行に折り返して 4px 動くが、想定利用環境ではないので許容。

### 13.2 説明文の書き直し

専門語と翻訳調を避けた。

| 直す前 | 直した後 |
|---|---|
| 脚の伸展を序盤で使い切る | 序盤で脚を使い切ってしまう |
| 肩が前へ滑り | 肩も前に出るため |
| バーが膝を越えたあたりで詰まる | 〜で止まる |
| 梃子だけがまっすぐ伸びる | 負担がまっすぐ増える |
| 脛が深く倒れる | 膝が前に出る |
| ファーストプルで床から切れない | 床から離れにくい |

主指標の文言も「脚の伸展を 46% 使用」→「**脚は 46% 伸びている**」に変えた。
「先食いしている」→「脚を使うのが早すぎる」、「脚が遅れている」→「脚が使えていない」。

### 13.3 「詳細」行（行見出し ＋ 3 点の箇条書き）

一段落の文だと読み上げにくく、どこを指しているかも分かりにくかった。
**体格・エラーと同じ「左に行見出し、右に中身」の形**に揃え、中身を 3 点の箇条書きにする。

```
体格（両者共通）  [標準][大腿が長い][体幹が長い]  腕 [短い][標準][長い]  [ナロー][ミドル][スモウ]
エラー          [なし][ぶっこ抜き][上体の立てすぎ][バーが遠い]  程度 [軽度][中等度][重度]
詳細            ・腰だけが先に上がり、上体が寝る
                ・序盤で脚を使い切るので、バーが膝を越えたあたりで止まる
                ・肩が前に出るぶん、バーが体から離れやすい
```

見出し名の候補は「起きていること」「コメント」「所見」「このフォームの特徴」を出し、
**「詳細」**に決めた（atsushi さん）。中立な語なので原因や修正キューをここに書きたく
なりやすい点だけ注意で、**現象だけを書く**規約（§7.3）は型コメントに明記してある。

行見出しの列幅は一番長い「体格（両者共通）」に合わせて `min-width: 9em` に広げた
（以前は 7em で、体格の行だけ中身の開始位置がずれていた）。

**3 点固定**は見た目の都合ではなく**レイアウトの要件**。点数が可変だと欄の高さが変わり、
図まで動く（§13.1）。エラー未選択のときも 3 点置く。型を
`readonly [string, string, string]` にしてあるので、3 点でないとコンパイルが通らない。

実測: 1400 / 1280 / 1920 / 1000 / 860 / 700 px のいずれでも、
4 項目を切り替えて図の位置・高さが 1px も動かない。
段落 1 行だった頃と比べた縦の消費増は 1280×620 で 23px（図 258→255px は
見出しを行内に畳んだぶん戻した）。

**未処理**: 主指標の 1 行だけが行見出しを持たず、左端から始まって列が揃っていない。
